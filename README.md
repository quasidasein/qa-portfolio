# Junior QA Engineer | Portfolio

Привет! В этом репозитории собраны артефакты моей практики в ручном тестировании. Я фокусируюсь на исследовании логики продуктов, клиент-серверном взаимодействии и создании качественной тестовой документации.

## 📁 Практические кейсы и артефакты

### 🎵 1. Автоматизация и контрактное тестирование API (Spotify Web API & CI/CD)
- **Формат:** Отдельный репозиторий с Postman-коллекцией, CI/CD пайплайном и зафиксированными дефектами спецификации.
- **Стек:** Postman, Newman (CLI Runner), GitHub Actions, Ubuntu Linux, REST API, OAuth 2.0 (Client Credentials Flow), JavaScript (Chai Assertion Library), JSON Schema.
- **Что реализовано:**
  * **CI/CD Пайплайн:** Настроен автоматический запуск тестов в headless-режиме через Newman на виртуальной машине Ubuntu Latest при каждом `push` в ветку `main`.
  * **Security First:** Спроектирована безопасная архитектура. Ключи приложения изолированы через GitHub Secrets (`SPOTIFY_CLIENT_ID`, `SPOTIFY_CLIENT_SECRET`), а публичный экспорт коллекции содержит только плейсхолдеры.
  * **Request Chaining:** Написан Post-response скрипт для динамического парсинга и сохранения Bearer-токена в переменные коллекции (TTL: 3600 сек).
  * **Тест-дизайн и BVA:** Покрыты позитивные и негативные сценарии (400, 401, 403 Forbidden, 404). Проведено граничное тестирование пагинации (`limit`, `offset`) и обработка невалидных параметров.
  * **Contract Testing & Schema Validation:** Валидация структуры ответов, типов данных и строгая проверка Enums.
  * **Выявление Contract Drift:** Обнаружены и задокументированы расхождения между официальной документацией Spotify и реальным поведением бэкенда (депрекейт обязательных полей, противоречия в диапазонах `limit`).
- **Смотреть проект:** https://github.com/quasidasein/spotify-api-postman-suite

### 🗓️ 2. Функциональное тестирование и аудит веб-платформы (Spaffy / EdTech)
* **Формат:** Исследовательское и функциональное тестирование модуля расписания с оформлением баг-репортов, доказательной базой и анализом рисков.
* **Стек и техники:** Chrome DevTools (Network, Console, Elements), анализ граничных значений (BVA), классы эквивалентности (EP), тестирование бизнес-логики и ролевой модели («Учитель» / «Ученик»).
* **Что реализовано:**
  * **Тест-дизайн и BVA:** Проведено граничное тестирование календарной сетки на стыке суток (23:55) и валидации допустимой длительности уроков.
  * **Локализация дефектов:** Выявлены и задокументированы 4 дефекта (рассинхронизация валидации длительности 1–4 мин, сбой бизнес-логики при пересечении занятий, скрытие карточки 23:55 в недельной сетке, сброс данных формы по клику на backdrop).
  * **Risk Assessment:** Сформированы рекомендации и зоны риска для продакшена (влияние Timezone Offset на отображение сетки, схлопывание UI-элементов).
- **Смотреть проект:** [Spaffy_Functional_Testing_Report.pdf](./Spaffy_Functional_Testing_Report.pdf)

### 📱 3. Исследовательское тестирование Telegram Mini App (BookingMaster / MastApp)
* **Формат:** Exploratory Testing (исследовательское тестирование) с сессионной видеозаписью процесса и анализом требований.
* **Описание:** Проведен аудит сервиса онлайн-записи. Применены техники тест-дизайна (BVA). Выявлены критические ошибки валидации полей, приводящие к серверным сбоям (статусы 500 и 400).
* **Материалы кейса:** [Видеосессия (26 мин), баг-репорты и документация](https://drive.google.com/drive/folders/1_b4I_qJr2xBw-EhkCibdFBeSD09ouFvy?usp=sharing)

### 📝 4. Тестовая документация: Web-регистрация (TuneCore)
* **Описание:** Проектирование тестовой документации (Test Design) для модуля регистрации веб-сервиса музыкальной дистрибуции.
* **Артефакты:** 
  * Набор из 15 атомарных **Test Cases** с детальным описанием шагов, тестовых данных, pre-conditions и ожидаемых результатов. Покрыты позитивные и негативные сценарии (анализ границ паролей, валидация email, reCAPTCHA, подтверждение пароля).
  * **Checklist** проверок формы регистрации с декомпозицией по полям и разделением на Positive/Negative проверки.
* **Смотреть артефакт:** [Чек-лист и тест-кейс.xlsx](./Чек-лист%20и%20тест-кейс.xlsx)

### 💾 6. Практика работы с базами данных (SQL)
* **Описание:** Написание сложных запросов к реляционным базам данных для решения классических QA-задач (поиск аномалий, проверка связей).
* **Стек и конструкции:** `INNER JOIN`, `LEFT JOIN` (поиск потерянных записей через `IS NULL`), вложенные подзапросы (Subqueries), агрегатные функции (`COUNT`, `SUM`, `AVG`), группировка (`GROUP BY`) и фильтрация групп (`HAVING`).
* **Смотреть артефакт:** [sql-queries.sql](./sql-queries.sql)

### 🌐 7. Базовое тестирование API и CRUD: Swagger Petstore
* **Файл:** `Petstore_API_Practice.postman_collection.json`
* **Стек:** Postman, JavaScript (Post-response scripts), REST API, JSON.
* **Что реализовано:**
  * Покрытие CRUD-операций для сущностей `User` и `Pet` (Swagger Petstore).
  * Динамическая авторизация (`Request Chaining`): автоматический парсинг токена сессии из ответа `/user/login` и передача в переменные коллекции.
  * Валидация статус-кодов (200, 201, 204), проверка структуры ответов (JSON schema) и бизнес-логики.
